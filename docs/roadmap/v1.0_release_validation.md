# Milestone: v1.0 Release Validation Plan (Final)

Following the completion of **Phases 1 through 5** and achieving `Production Candidate (v0.4.0)` status, the **v1.0 Release Validation Milestone** transitions GITLINK from feature development to validating distributed consistency, chaos recovery, long-running stability, security regression prevention, and performance benchmarking.

## 1. Multi-Node Integration & End-to-End Environment
- **Docker Compose Topology**: Launch `api-server`, `git-server`, `libp2p-node`, and `postgres` together in a single container network.
- **End-to-End Flow**: Verify `HTTP Request -> API -> Git Server -> IPC -> libp2p -> PostgreSQL` in live containers.

---

## 2. Multi-Node P2P Replication, Convergence & Consistency
- **Topology Test**: Spin up 3 independent GITLINK peer instances (`Node A`, `Node B`, `Node C`).
- **Distributed Replication & Convergence**:
  1. Commit on `Node A` -> Replicate to `Node B` and `Node C`.
  2. Disconnect `Node B` (offline mode) -> Commit on `Node A` & `Node C` (creating divergent graphs).
  3. Reconnect `Node B` -> Trigger sync worker.
  4. **Convergence Gates**: 
     - Verify every node reaches the exact same commit graph hash.
     - Verify zero duplicate synchronization tasks are created in the database.
     - Verify no infinite conflicting replay loops occur between nodes.
     - **Bounded Time SLA**: Convergence must fully complete within **30 seconds** after the final node reconnects under the baseline test workload.

---

## 3. Chaos Testing & Component Failure Recovery
- **PostgreSQL Crash Recovery**: Kill `postgres` during active sync task execution -> Restart DB -> Verify worker recovers without task corruption.
- **Git Engine Failure**: Terminate `git-server` during push/pull -> Verify IPC timeout handling and zero corrupted repositories.
- **libp2p Daemon Crash**: Kill `libp2p-node` during P2P dispatch -> Verify `SyncTask` transitions to `retry_scheduled` with backoff.
- **WebSocket Reconnect**: Restart `api-server` -> Reconnect client with `last_event_id` -> Verify unread notification stream replay.

---

## 4. Long-Running Stability (Soak Testing)
- **Soak Test Procedure**: Run the 3-node network continuously for 12+ hours under synthetic load.
- **Resource Stability Gates**:
  - **Memory Stability**: RSS memory usage must plateau rather than grow continuously.
  - **Thread Boundedness**: Goroutine and system thread counts must remain within bounded limits.
  - **Handle Leak Prevention**: File descriptor and network socket counts must not increase continually.
  - **Connection Boundedness**: Database connection pool must return to a steady-state idle pool count.
  - **Queue Consistency**: No synchronization tasks dropped; zero database record corruption.

## 6. Security Regression Verification Checklist

| Test Scenario | Expected Outcome |
| :--- | :--- |
| **Unauthenticated Git HTTP** | Verify anonymous access to Git smart routes returns `401 Unauthorized` / `403 Forbidden`. |
| **Team RBAC Enforcement** | Verify authorized users succeed in executing Git push actions, and unauthorized users are denied. |
| **Admin Endpoint Bypass** | Verify non-admin users cannot access `/api/v1/sync/dlq/replay` or worker restart endpoints. |
| **WebSocket Event Privacy** | Verify that `last_event_id` reconnect requests retrieve ONLY the authenticated user's notification stream. |
| **Path Traversal Sanitization** | Verify payload traversal queries (`../repo`) are rejected by Rust input sanitization module. |

---

## 7. Known Limitations & Scope Boundaries
- **Maximum Peer Count**: The v1.0 release is validated for meshes up to 5 concurrent active peers.
- **Byzantine/Malicious Peers**: Protecting against malicious peer nodes injecting corrupted commit hashes is out-of-scope (Zero-Trust applies to API clients, P2P network assumes cooperative authenticated peers).
- **WAN Environments**: Simulation is performed under high-latency simulated LAN environments; strict wide-area network partition characteristics are not fully validated.

---

## 8. Go/No-Go Release Decision Framework

Before releasing GITLINK v1.0, the **Release Validation Report** must compile:
- Benchmark environment hardware specifications.
- Actual results for the Performance SLAs.
- Zero open critical/high security issues.
- Successful verification of all convergence and chaos recovery scenarios.
